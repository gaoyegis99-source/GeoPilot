# P4-15 检查报告持久化

Agent-F 实施，建议 `REVIEW`。依据 V2.0 §7.9、§8.1 和 §8.7 实现检查报告与运行双状态的持久化。[原子任务](../../plans/04_TASKS/P4/P4-15.md)

## 接口与存储

`summarize_check_status` 接收已完成规则的 JSON 字典。每项需要布尔值 `passed` 和严重级别 `blocking` 或 `warning`。阻断项失败汇总为 `FAILED`，仅警告项失败汇总为 `WARNING`，全部通过汇总为 `PASSED`。检查中断汇总为 `NOT_CHECKED`，报告可保存已完成规则、待检查规则和中断原因。

`CheckReport` 保存报告 ID、运行 ID、最终检查状态、完整 JSON、规则版本快照和创建时间。SQLite v4 追加 `check_report` 表，通过外键归属精确运行。最终报告 ID 唯一，已有报告保持可查询。表约束为后续排队与重查预留 `QUEUED` 和 `CHECKING`，这两种状态的报告内容为空。

`publish_report(connection, report, *, error=None)` 由调用方开启 SQLite 写事务。服务在同一事务保存报告并更新 `run.check_status`、`run.current_report_id` 和 `run.error_json`。报告插入与运行更新使用同一保存点，运行更新失败时回滚本次发布。运行 `SUCCEEDED` 可与检查 `FAILED`、`WARNING` 或 `NOT_CHECKED` 共存。

`get_current_report(connection, run_id)` 返回运行当前引用的最终报告。`list_report_ids(connection, run_id)` 按创建时间和 ID 降序返回已发布报告 ID。查询忽略排队和检查中的预留记录。SQLite 验证使用临时数据库，HTTP 和真实 GIS 场景 T16 的验收由应用集成覆盖。
